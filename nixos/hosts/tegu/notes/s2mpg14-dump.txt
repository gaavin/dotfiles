WHAT THIS ESTABLISHES

- Both PMICs answer on ACPM channel 2, speedy 0 and 1.
- The first four bytes of common are identical on both chips
  (fd f9 57 41), and byte 4 differs (cd vs cf) -- a plausible chip ID
  field, though nothing here confirms that reading.
- The layout is NOT S2MPG10's. From +0x18 the bucks read as (value, 0xf8)
  pairs; S2MPG10 has CTRL/OUT1/OUT2 triplets there. Attaching the S2MPG10
  driver would have written to the wrong registers, not merely risked it.

WHAT THIS DOES NOT ESTABLISH, AND MUST NOT BE ASSUMED

Where LDO4M and LDO25M are. If S2MPG14 placed L1M_CTRL at 0x40 as S2MPG10
does, then with S2MPG10's encoding (bit 7 = enable, bits [5:0] = voltage)
LDO4M would be +0x43 = 0x2c and LDO25M would be +0x58 = 0x44, both with
bit 7 clear, i.e. both off -- which is what the unpowered-touch-part theory
predicts.

That is suggestive and nothing more. Against it: +0x44..0x48 reads
7f cc ff ff ff, and three consecutive 0xff bytes look far more like
interrupt masks than LDO controls, which would put the block boundary
somewhere else. The buck layout already differs from S2MPG10, so there is
no reason to expect the LDO base to match.

Writing an enable to a guessed offset would be a write into the PMIC that
powers the whole board, including the rails it boots from. The map has to
come from a source -- Google publishes the S2MPG14 headers in a
google-modules repo that is not checked out here -- or from a differential
read against a known change. Not from this table plus optimism.
