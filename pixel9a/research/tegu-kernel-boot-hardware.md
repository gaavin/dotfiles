# Google Pixel 9a (`tegu`, Tensor G4 / `zumapro`) — Linux-on-phone feasibility findings

Research date: ~September 2026. Every claim below carries an inline source. Items that are inference rather than directly sourced fact are marked **(speculation)**.

---

## 1. Upstream mainline Linux support for Tensor G4 / `zumapro`

**Bottom line:** As of September 2026 (Linux master ≈ v7.3-rc4, stable v7.2.x) there is **no mainline Linux support for Tensor G4 / `zumapro` and no device tree for `tegu` or any Tensor G4 phone**. The only Google Tensor platform upstream is the older **GS101 (Tensor G1, Pixel 6)**. `tegu` itself has **no postmarketOS port at all**; the closest thing is an out-of-tree "mainline" fork for the Pixel 9 (`tokay`, same SoC) that boots to a `simpledrm` console.

Evidence:

- The mainline device-tree directory `arch/arm64/boot/dts/exynos/google/` contains **only GS101** files: `gs101.dtsi`, `gs101-oriole.dts`, `gs101-raven.dts`, `gs101-pixel-common.dtsi`, `gs101-pinctrl.*`. No `zumapro*.dts`, no `tegu`. ([git.kernel.org tree listing](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/arch/arm64/boot/dts/exynos/google))
- Cross-referencing the Linux v7.2.7 source, the identifier `zumapro` does not exist anywhere in the tree (Elixir returns 404). ([elixir.bootlin.com v7.2.7 ident zumapro](https://elixir.bootlin.com/linux/v7.2.7/A/ident/zumapro))
- postmarketOS wiki for **google-tegu**: *"This device is marked as not booting… no port as far as I know"*, **Mainline: no**, last edited 8 Aug 2026. ([postmarketOS: Google Pixel 9a (google-tegu)](https://wiki.postmarketos.org/wiki/Google_Pixel_9a_(google-tegu)))
- postmarketOS wiki for the SoC: **Tensor G4 = codename `zumapro`, model GS401**; the hardware table lists **every** component (CPU, UART, storage, USB, display, GPU, pinctrl, I²C, thermal, Wi-Fi/BT, modem, GPS, camera, suspend) as **"Untested"**, and it has no mainline note. ([postmarketOS: Google Tensor G4](https://wiki.postmarketos.org/wiki/Google_Tensor_G4))
- The Pixel 9 (`google-tokay`, same Tensor G4) page is the most advanced data point: *"Kernel compiles, boots, and simpledrm works"*, **Mainline: yes**, kernel **7.1-rc2**, but Screen/Touchscreen only *Partial*, and **3D, Audio, Camera, Wi-Fi, Bluetooth, GPS, NFC, modem, USB-OTG, DP, fingerprint, sensors all Broken**. It links a WIP out-of-tree kernel. ([postmarketOS: Google Pixel 9 (google-tokay)](https://wiki.postmarketos.org/wiki/Google_Pixel_9_(google-tokay)))
- That WIP kernel is `orgwithsomething/linux-zumapro` — a **fork of torvalds/linux** (not upstream), branches `tokay` / `tokay-old`, last pushed 2026-09-14. ([GitHub orgwithsomething/linux-zumapro](https://github.com/orgwithsomething/linux-zumapro), [branches via API](https://api.github.com/repos/orgwithsomething/linux-zumapro/branches))

### What actually exists upstream (GS101 / Tensor G1, not G4)

The Linaro GS101 bring-up series added, in mainline: **CPUs, pinctrl, clock controllers (CMU_TOP/MISC/APM), watchdog, USI UART, GPIO, PMU, sysreg** — enough to boot an upstream kernel to a busybox initramfs; mainline Pixel 6 support landed in **Linux 6.8**. ([LKML v5 cover letter](https://lore.kernel.org/linux-arm-kernel/860ca122a08bbce70b27d8880c621f0d12ddd2a5.camel@linaro.org/T/), [Phoronix: Linux 6.8 GS101/Pixel 6](https://www.phoronix.com/news/Linux-6.8-GS101-SoC-Pixel-6))

Subsequently added upstream for GS101: **UFS** (`ufs-exynos` / `google,gs101-ufs-phy`) ([LKML v3 "ufs-exynos support for Tensor GS101"](https://lkml.org/lkml/2024/4/26/447), [patchew](https://patchew.org/linux/20240426122004.2249178-1-peter.griffin@linaro.org/)), **thermal TMU** ([LKML "thermal: samsung: Add support for Google GS101 TMU"](https://lore.kernel.org/linux-pm/d3dedf5e-ada3-4d33-b1a5-7556ba80ffb1@linaro.org/T/)), and **DWC3 USB** glue. Linux 7.0 added *"a USB driver for Google Tensor SoCs"* — a DWC3-based controller for Tensor ([Phoronix: Linux 7.0 USB](https://www.phoronix.com/news/Linux-7.0-USB), [DevBytes summary](https://devbytes.co.in/news/linux-v70-to-support-googles-tensor-soc)).

**These drivers are keyed to `google,gs101-*` compatibles.** Tensor G4 is a different (Exynos-2400-derived) platform; reusing the Exynos/Samsung-family drivers on `zumapro` is plausible **(speculation)** but has **no upstream DT or compatible strings**, and postmarketOS marks all of it "Untested".

- **Display:** mainline GS101 DT has no DSI/DPU display pipeline; the tokay port only gets `simpledrm`. No mainline display driver for Tensor.
- **GPU (Mali-G715 MP7):** G715 is a 5th-gen CSF Mali, i.e. the class of GPU that upstream **panthor** targets (panthor handles CSF firmware/exception model — see [`panthor_device.c`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/drivers/gpu/drm/panthor/panthor_device.c)). But there is **no Tensor G4 GPU integration** upstream and pmOS tokay reports 3D as **Broken**. Treat "panthor can drive G715" as true for the hardware family **(speculation on Tensor G4 specifically)**.
- **Storage/UFS:** upstream `ufs-exynos` supports GS101; whether the zumapro UFS controller is compatible is undocumented/unported.

## 2. Google's official Android kernel source for Pixel 9a / Tensor G4

**Bottom line:** Yes, Google publishes it; it is **GKI-based on `android14-6.1` (kernel 6.1)**. The official build branch for the Pixel 9a is **`android-gs-tegu-6.1-android16`**, synced via `repo init -u https://android.googlesource.com/kernel/manifest -b <branch>`.

- Google's official table: **Pixel 9a (tegu) → repository branch `android-gs-tegu-6.1-android16` → GKI kernel `android14-6.1`**. ([source.android.com: Build Pixel kernels](https://source.android.com/docs/setup/build/building-pixel-kernels)) The same page notes that *only Pixel 6/6 Pro* are supported by upstream mainline, and documents the `kernel/manifest` repo-init flow.
- The platform repo namespace for Tensor G4 is **`kernel/devices/google/zumapro`** on android.googlesource.com (e.g. it carries `android-gs-caimito-6.1-android16` and other Pixel 9 device branches). ([android.googlesource.com/kernel/devices/google/zumapro](https://android.googlesource.com/kernel/devices/google/zumapro/)) *Note: this mirror returned HTTP 503 during this research; the branch/repo naming is corroborated by search-indexed refs ([example ref](https://android.xilinx.googlesource.com/kernel/devices/google/zumapro/+/refs/heads/android-gs-caimito-6.1-android16)) and by AOSP's in-tree kernel path below.*
- AOSP/LineageOS tree layout confirms it: `TARGET_KERNEL_DEVICE := tegu`, `TARGET_KERNEL_DIR := device/google/tegu-kernels/6.1`, `TARGET_KERNEL_PLATFORM_SOURCE := google/gs-6.1`, `TARGET_LINUX_KERNEL_VERSION := 6.1`. ([LineageOS `device-tegu.mk`](https://raw.githubusercontent.com/LineageOS/android_device_google_tegu/lineage-23.2/device-tegu.mk))
- LineageOS wiki lists tegu kernel **6.1**, source [`LineageOS/android_kernel_google_gs-6.1_manifest`](https://github.com/LineageOS/android_kernel_google_gs-6.1_manifest). ([LineageOS wiki: Info about tegu](https://wiki.lineageos.org/devices/tegu/))
- Google's **driver binaries** (proprietary firmware/vendor blobs) are published per device/build — the page has multiple *"Pixel 9a binaries"* entries. ([developers.google.com/android/drivers](https://developers.google.com/android/drivers))
- **`kerneltoast/android_kernel_google_tensynos`** is a **third-party** common-kernel fork (not Google's): its repo describes it as *"Pixel 7, 8, and 9 series kernel."* The older name `android_kernel_google_zumapro` now redirects to it. ([GitHub kerneltoast/android_kernel_google_tensynos](https://github.com/kerneltoast/android_kernel_google_tensynos), [relatedrepos](https://relatedrepos.com/gh/kerneltoast/android_kernel_google_zumapro))
- **Is it GKI-based?** Yes. tegu builds `TARGET_NO_KERNEL := true` / `BOARD_USES_GENERIC_KERNEL_IMAGE := true` against the `android14-6.1` GKI with Pixel modules in `vendor_boot`/`vendor_dlkm`/`system_dlkm`. ([LineageOS BoardConfig-common.mk](https://raw.githubusercontent.com/LineageOS/android_device_google_zumapro/lineage-23.2/BoardConfig-common.mk))

## 3. Bootloader / verified boot constraints on Pixel 9a

**Bottom line:** `fastboot flashing unlock` works on an unlockable tegu. OEM unlocking is **gated by the device's carrier id** (carrier SKUs grey it out / require a server check); a **non-stock AVB key can be installed** and is what custom OSes like GrapheneOS use; a **locked bootloader enforces verified boot** and blocks flashing entirely; and unlocking produces a visible boot warning.

- **Unlock works:** documented in the tegu-specific instructions — enable Developer Options → OEM unlocking, `adb reboot bootloader`, `fastboot flashing unlock`, confirm on-screen (wipes data). ([postmarketOS google-tegu](https://wiki.postmarketos.org/wiki/Google_Pixel_9a_(google-tegu)); [LineageOS tegu install](https://wiki.lineageos.org/devices/tegu/install); [GrapheneOS CLI install](https://grapheneos.org/install/cli))
- **Carrier gating:** *"Carrier variants of Pixels use the same stock OS and firmware with a non-zero carrier id flashed onto the persist partition in the factory. The carrier id activates carrier-specific configuration in the stock OS including disabling carrier and bootloader unlocking."* On such SKUs, **enabling OEM unlocking requires internet access** so the stock OS can check whether the device was sold locked. ([GrapheneOS CLI install](https://grapheneos.org/install/cli), [GrapheneOS web install](https://grapheneos.org/install/web)) GrapheneOS's supported-device list repeats this for all Pixels. ([GrapheneOS FAQ](https://grapheneos.org/faq))
- **Custom AVB key:** yes. GrapheneOS installs its own verified-boot public key (flashed to the secure element) and documents the reverse with **`fastboot erase avb_custom_key`** before returning to stock. The alternate-OS key hash is shown as a **yellow boot notice** on 6th-gen+ Pixels (Pixel 9a's official GrapheneOS key hash is `0508de44…b589445b`). ([GrapheneOS CLI install](https://grapheneos.org/install/cli))
- **Verified boot enforcement:** *"Locking the bootloader is important as it enables full verified boot. It also prevents using fastboot to flash, format or erase partitions."* The final firmware stage verifies the OS using a key from the secure element (stock uses a hard-wired key; GrapheneOS flashes its own). ([GrapheneOS CLI install](https://grapheneos.org/install/cli))
- **Booting with an unlocked bootloader / custom images:** the bootloader interface shows *"a red warning triangle and the words Fastboot Mode"*; loading an alternate OS shows the yellow notice with the verified-boot key ID. The exact boot-splash string (commonly "your device software can't be checked for corruption") is widely reported but I could not verify it from a primary source here. ([GrapheneOS web install](https://grapheneos.org/install/web))
- **`--disable-verity` / `--disable-verification`:** the Tensor ABL exposes vendor equivalents **`fastboot oem disable-verity`**, **`fastboot oem disable-verification`** (and `enable-verity` / `enable-verification`), all tagged **`FB_CMD_FORBID_LOCKED`** (unavailable when locked). This comes from a reverse-engineered **Pixel 6a** `abl` dump, so applicability to tegu's ABL is highly likely but **not directly confirmed (speculation)**. ([XDA: fastboot oem commands](https://xdaforums.com/t/fastboot-oem-commands.4714256/))
- AVB layout on tegu chains `vbmeta`, `vbmeta_system` (system, system_dlkm, system_ext, product), `vbmeta_vendor` (vendor), plus boot/init_boot chain partitions; `--flags 3` (disable-verity/verification) is used when AVB is off. ([LineageOS BoardConfig-common.mk](https://raw.githubusercontent.com/LineageOS/android_device_google_zumapro/lineage-23.2/BoardConfig-common.mk))

## 4. Partition layout and custom-OS installation

**Bottom line:** tegu is **A/B with a dynamic `super`** (~8.53 GB) holding the logical read-only partitions. There is **no dedicated recovery partition** — recovery lives in `vendor_boot`. A custom OS is installed by flashing `boot`/`dtbo`/`vendor_kernel_boot`, flashing recovery into `vendor_boot`, then writing the logical partitions (sideload / `update_engine` / `fastbootd`), never by hand-editing `system`/`vendor` in place.

Verified from the LineageOS Pixel 9-series board config (authoritative, AOSP-derived):

- **A/B:** `AB_OTA_UPDATER := true`. ([BoardConfig-common.mk](https://raw.githubusercontent.com/LineageOS/android_device_google_zumapro/lineage-23.2/BoardConfig-common.mk))
- **`super`:** `BOARD_SUPER_PARTITION_SIZE := 8531214336` (~8.53 GB), group **`google_dynamic_partitions`** (size ~8.527 GB), containing logical partitions **`system`, `system_dlkm`, `system_ext`, `product`, `vendor`, `vendor_dlkm`**; `BOARD_SUPER_PARTITION_ERROR_LIMIT := 8006926336`. ([BoardConfig-common.mk](https://raw.githubusercontent.com/LineageOS/android_device_google_zumapro/lineage-23.2/BoardConfig-common.mk))
- **Physical partitions referenced for boot/OS:** `boot`, `init_boot`, `vendor_boot`, `vendor_kernel_boot`, `dtbo`, `vbmeta`, `vbmeta_system`, `vbmeta_vendor`, `pvmfw`, plus `super`, `userdata`, `metadata`, `persist`; sizes e.g. boot `0x04000000`, init_boot `0x800000`, vendor_boot `0x04000000`, dtbo `0x01000000`, pvmfw `0x00100000`. Firmware partitions (`abl`/`bl1`/`bl2`/`bl31`/`gsa`/`tzsw`/`modem`/`radio`, etc.) are flashed by the factory `flash-all` script. ([BoardConfig-common.mk](https://raw.githubusercontent.com/LineageOS/android_device_google_zumapro/lineage-23.2/BoardConfig-common.mk); [Google's per-device kernel-partition table](https://source.android.com/docs/setup/build/building-pixel-kernels) lists boot/dtbo/vendor_boot/vendor_dlkm for Pixel 9 devices.)
- **No recovery partition:** `BOARD_MOVE_RECOVERY_RESOURCES_TO_VENDOR_BOOT := true` and `TARGET_NO_BOOTLOADER := true`. LineageOS/crDroid explicitly install **`vendor_boot.img` as the recovery image**. ([BoardConfig-common.mk](https://raw.githubusercontent.com/LineageOS/android_device_google_zumapro/lineage-23.2/BoardConfig-common.mk); [LineageOS tegu install](https://wiki.lineageos.org/devices/tegu/install); [crDroid tegu install](https://crdroid.net/tegu/12/install))
- **Typical install:** `fastboot flashing unlock` → `fastboot flash boot boot.img` → `fastboot flash dtbo dtbo.img` → `fastboot flash vendor_kernel_boot vendor_kernel_boot.img` → `fastboot flash vendor_boot vendor_boot.img` (recovery) → boot recovery → **Factory reset / Format data** → **`adb sideload <rom>.zip`** (this writes the logical `system`/`vendor`/… partitions via `update_engine`). ([LineageOS tegu install](https://wiki.lineageos.org/devices/tegu/install); [crDroid tegu install](https://crdroid.net/tegu/12/install)) GrapheneOS instead flashes a whole factory image with `flash-all.sh`. ([GrapheneOS CLI install](https://grapheneos.org/install/cli))
- **Constraints on replacing `system`/`vendor`:** they are **logical partitions inside `super`**, not standalone block devices. They must be (re)sized/written through the dynamic-partition tooling — a rebuilt `super.img`, `super_empty.img`, or **`fastbootd`** in userspace — and the total is bounded by the fixed `super` size (~8.53 GB, ~500 MB error headroom). AOSP states the super partition contains the logical partitions, may be sized/resized with the provided tooling, and that flashing them requires fastbootd. ([AOSP: Implement dynamic partitions](https://source.android.com/docs/core/ota/dynamic_partitions/implement), [AOSP: fastbootd](https://source.android.com/docs/core/architecture/bootloader/fastbootd))
- Firmware (modem, bootloader, ADSP/AOC, etc.) is **not** replaceable outside Android/AOSP images; custom OSes ship Google's signed firmware blobs and only replace the kernel/OS partitions. ([developers.google.com/android/drivers](https://developers.google.com/android/drivers))

## 5. Pixel/Tensor-specific hardware barriers to non-Android Linux

**Bottom line:** the SoC-adjacent accelerators and radios are the blockers. Several have drivers **only as Google out-of-tree kernel modules in the Android tree**, all require **signed firmware**, and none are in mainline: EdgeTPU (`abrolhos`), the GXP DSP used by the camera pipeline (`gxp`), the Titan M2 secure element (`gsa`/`gsc`), the Exynos 5400 modem, and the Broadcom BCM4390Y Wi-Fi/BT. Display and GPU likewise have no working Linux stack on Tensor G4 today.

Per the postmarketOS Tensor G4 hardware table, the Pixel 9a contains: **Edge TPU ("Rio")**, **Google Titan M2 (H1D3M2)**, **Samsung Exynos 5400 modem** (with NB-IoT/NR NTN satellite), **USI/Broadcom BCM4390Y Wi-Fi/BT**, and the Google camera/ISP complex. ([postmarketOS: Google Tensor G4](https://wiki.postmarketos.org/wiki/Google_Tensor_G4))

- **EdgeTPU (NPU) — `abrolhos` driver:** lives in Google's out-of-tree Android module tree at `kernel/google-modules/edgetpu/abrolhos` (e.g. `drivers/edgetpu/abrolhos-firmware.c`, `abrolhos-pm.c`). **Not upstream**, and it loads **firmware**. ([abrolhos-firmware.c](https://android.googlesource.com/kernel/google-modules/edgetpu/+/e6dc812c2244d17c2fc14ab6f51845bf52e4b4b1/drivers/edgetpu/abrolhos-firmware.c), [abrolhos-pm.c](https://android.googlesource.com/kernel/google-modules/edgetpu/+/1fe188fef7fc27ec88d2b47e3aafa01a6a991f8d/drivers/edgetpu/abrolhos-pm.c))
- **GXP DSP (camera/offload) — `gxp` driver:** out-of-tree at `kernel/google-modules/gxp/zuma` with its own sysfs ABI; **not upstream**. Google's userspace camera stack (`libgxp` + camera HAL) is proprietary; there is no public Linux userspace for it. ([sysfs-class-gxp in kernel/google-modules/gxp/zuma](https://android.git.googlesource.com/kernel/google-modules/gxp/zuma/+/refs/tags/android-16-preview-1_r0.9/Documentation/ABI/stable/sysfs-class-gxp))
- **Titan M2 / GSA / GSC secure element:** no mainline Linux driver. The ABL exposes `fastboot oem gsc …` / `fastboot oem gsa …` controls (version, secure-link, AVB state, UART passthru), i.e. it is reachable from the bootloader but not usable as a Linux device; public work is *reverse engineering* of its firmware, not a driver. ([XDA fastboot oem commands](https://xdaforums.com/t/fastboot-oem-commands.4714256/), [CCC: Reverse engineering the Titan M2 firmware](https://cfp.cccv.de/media/39c3/submissions/ZH8KQV/resources/Titan_M2_Reverse_Engineering2_J8udjIi.pdf))
- **Modem (Samsung Exynos 5400):** no mainline driver; Android uses vendor RIL (`ENABLE_VENDOR_RIL_SERVICE := true`). It needs proprietary, signed firmware and an Android userspace stack. ([LineageOS BoardConfig-common.mk](https://raw.githubusercontent.com/LineageOS/android_device_google_zumapro/lineage-23.2/BoardConfig-common.mk)) The ABL exposes its UART as the `cp` interface, confirming it is a separate signed-firmware processor. ([XDA fastboot oem commands](https://xdaforums.com/t/fastboot-oem-commands.4714256/))
- **Connectivity / ADSP-class DSPs (AOC, GSA boot path):** the downstream kernel command line includes `aoc_core.aoc_enable_gsa_boot=1`, i.e. an Android-tree AOC driver participates in booting the security subsystem; these are out-of-tree, firmware-loading drivers. ([LineageOS BoardConfig-common.mk](https://raw.githubusercontent.com/LineageOS/android_device_google_zumapro/lineage-23.2/BoardConfig-common.mk))
- **Wi-Fi/BT (Broadcom BCM4390Y):** no mainline driver for this part; Pixel uses Broadcom's out-of-tree `bcmdhd` plus firmware. **Not verified specifically for BCM4390Y** (the part ID comes from postmarketOS); **(speculation)** based on the platform's standard out-of-tree Broadcom stack. ([postmarketOS: Google Tensor G4](https://wiki.postmarketos.org/wiki/Google_Tensor_G4))
- **Camera ISP:** no mainline driver; it is driven through the GXP/firmware + proprietary camera HAL path above, so an Android-free camera is not feasible today. ([gxp sysfs ABI](https://android.git.googlesource.com/kernel/google-modules/gxp/zuma/+/refs/tags/android-16-preview-1_r0.9/Documentation/ABI/stable/sysfs-class-gxp))
- **Display:** no mainline DSI/DPU driver; the best current result on the same SoC is `simpledrm` on tokay. ([postmarketOS: Google Pixel 9 (google-tokay)](https://wiki.postmarketos.org/wiki/Google_Pixel_9_(google-tokay)))
- **GPU:** upstream panthor is the right family for Mali-G715, but no Tensor G4 integration exists; pmOS tokay reports 3D acceleration **Broken**. ([postmarketOS tokay](https://wiki.postmarketos.org/wiki/Google_Pixel_9_(google-tokay)))

## 6. Debug UART on Pixel/Tensor

**Bottom line:** the Tensor ABL exposes a real UART subsystem, including `fastboot oem uart list/enable/disable/mux` and a `dbgc uart-console` control, with the application/kernel console on the **`apc`** interface (disabled by default, 115200 baud). All of these are **`FB_CMD_FORBID_LOCKED`**, i.e. they require an unlocked bootloader. Physically the console comes out on the **USB-C SBU pins**, requiring a breakout / "USB-Cereal"-style adapter plus a **1.8 V** USB-TTL dongle. Output is available from the bootloader through the kernel. **Whether this exact path works on tegu is not publicly confirmed** — the most recent public tegu-specific request (April 2026) had no confirmed answer.

- **ABL UART commands** (`fastboot oem uart …`): `list`, `enable [selection] [loglevel]`, `disable [selection]`, `mux <selection>`, `virt-enable/virt-disable`; plus `fastboot oem dbgc uart-console [enable|disable]`, `fastboot oem dbgc uart-mux`, and `fastboot oem gsc uart-passthru`. ([XDA: fastboot oem commands](https://xdaforums.com/t/fastboot-oem-commands.4714256/))
- **Interfaces and defaults** from `fastboot oem uart list` on a Tensor Pixel: `apc` (disabled by default, 115200), `aoc` (enabled, 115200), `gsa` (enabled, 115200), `gsc` (enabled, 921600 — Titan M2), `cp` (enabled, 115200 — Samsung modem), `dbgc` (enabled, 115200), `tpu` (enabled, 921600). Enabling `apc` flips the fastboot UI from `UART: disabled` to `UART: 115200`, and it is the interface that carries **kernel boot logs**. ([XDA: fastboot oem commands](https://xdaforums.com/t/fastboot-oem-commands.4714256/))
- **Unlock requirement:** in the same ABL command table the `uart` command is flagged `FB_CMD_FORBID_LOCKED`, so it only works with an unlocked bootloader (like `dbgc`, `gsc`, `gsa` subcommands). ([XDA: fastboot oem commands](https://xdaforums.com/t/fastboot-oem-commands.4714256/)) *Caveat: this dump is from a **Pixel 6a** (Tensor G1) `abl`; the Tensor ABL is shared across generations, so it very likely applies to tegu, but this is not confirmed for tegu (speculation).*
- **Physical access:** Pixel debug UART is on the **USB-C SBU1/SBU2 pins** with a **1.8 V logic level**, read out with a USB-C breakout/`USB-Cereal` board and a 1.8 V USB-to-TTL adapter. This was validated upstream for the **Pixel 3a/3a XL** (sdm670) by the mainline patch series *"Add support and enable the debug UART in the Pixel 3a and Pixel 3a XL"* (v5), whose cover letter states full kernel logs were captured through the SBU pins. ([patchew: Pixel 3a debug UART v5](https://patchew.org/linux/20260926-pabloyoyoista-debug-uart-on-rdacayan-next-v5-0-db74ff64a7e7@samcday.com/))
- **Bootloader-stage output:** yes — the ABL UART subsystem and `gsc/gsc_uart_passthru`, `dbgc uart-console` commands operate before the kernel, and the fastboot screen itself reports UART state; Google's Pixel kernel docs discuss enabling UART to capture the kernel boot log. ([XDA: fastboot oem commands](https://xdaforums.com/t/fastboot-oem-commands.4714256/), [source.android.com: Build Pixel kernels](https://source.android.com/docs/setup/build/building-pixel-kernels))
- **tegu-specific status:** a public GrapheneOS-forum thread (29 Apr 2026) asks exactly these questions for **Pixel 9a (tegu)** — whether `fastboot oem uart enable` still works, whether SBU TX/RX assignments/1.8 V are unchanged, and for any working capture — and, in the content retrieved, contains **no confirmed answer**. ([GrapheneOS forum: UART/serial console on Pixel 9a](https://discuss.grapheneos.org/d/35092-uartserial-console-on-pixel-9a-tegu-possible-hardware-setup)) **Treat "works on tegu" as unverified.**

### Practical note on SWD/JTAG
The same ABL exposes `dbgc sjtag-ap` / `dbgc sjtag-gsa` and `fastboot oem gsc sjtag-cfg`, i.e. ARM **SWD/JTAG-ish debug** controls gated behind the unlocked bootloader — relevant if UART alone is insufficient. ([XDA: fastboot oem commands](https://xdaforums.com/t/fastboot-oem-commands.4714256/))

## Overall feasibility summary for Linux-on-tegu (Sept 2026)

| Area | Status |
|---|---|
| Upstream mainline for Tensor G4 | **None** (no DT, no `zumapro` compatibles). Tensor G1/GS101 only. |
| A working non-Android kernel | **WIP, out-of-tree** (same-SoC `tokay` fork boots to `simpledrm`); no `tegu` port. |
| Bootloader unlock | **Yes** on non-carrier SKUs; carrier SKUs gated by persist carrier id + server check. |
| Custom AVB key / custom OS | **Yes** (`avb_custom_key`); custom Android OSes are routine on tegu. |
| Boot a custom *Linux* kernel | Possible in principle, but you must supply DT and all drivers yourself; display, GPU, radios and storage support are missing/untested. |
| Firmware-dependent blocks (TPU, GXP/camera, Titan, modem, Wi-Fi/BT, AOC/ADSP) | **No public Linux drivers; signed-firmware-only, out-of-tree Android modules.** |
| Debug UART | **Exists in ABL, unlocked-only, SBU pins @1.8 V**; not confirmed on tegu. |

**Bottom line:** the Pixel 9a is a fine Android/custom-Android target (LineageOS 23.2, GrapheneOS, crDroid all support `tegu`), but as a Linux-on-phone target in 2026 it is **early**: Tensor G4 has no mainline SoC or board support, and the interesting blocks (display, GPU, camera/ISP, TPU, modem, Wi-Fi/BT, secure element) are all downstream, firmware-dependent, out-of-tree, or absent. Only the older Tensor G1 (Pixel 6) has mainline support, and even that is partial.
